1.1、数据是怎么处理的？
我们的数据采用JSONL格式，包含source（来源信息）、doc（文档内容）、labels（标注信息，包括评分和评分理由）三个核心字段，我们对网页内容做提取，进行Unicode归一化处理，重点解决重复内容问题。由于很多新闻都是对同一事件进行报道，报道内容大同小异但又不会完全相同，采用精确指纹（例如SHA-256）无法过滤到类似的新闻，我们采用了近似指纹，具体来说我们采用了一种联合阈值策略，设计了"标题相似度 + 正文重合度 + 语义相似度"的三重阈值策略，使用三种算法处理不同维度的相似性：
标题相似度计算：使用编辑距离和余弦相似度计算，阈值设为0.8。这部分主要处理标题的文本相似性，能够识别完全相同的标题或高度相似的标题变体。
正文重合度计算：使用MinHash算法估计的Jaccard相似度，阈值设为0.7。MinHash能够快速计算两个文档的特征集合重叠程度，特别适合处理长文本的相似性判断。
语义相似度计算：使用SimHash算法 64 位指纹的汉明距离来计算语义层面的相似性，阈值设为3。SimHash能够捕捉文本的语义特征，即使表达方式不同，只要核心内容相似，也能被识别出来。
应用三重阈值：只有当标题相似度 > 0.8 且正文重合度 > 0.7 且 SimHash ≤ 3 时，才判定为重复内容。经过过滤后，剩余约10万条新闻。
除了解决新闻重复问题以外，还做了数据标准化，比如统一时间格式为ISO-8601，统一货币代码为ISO 4217标准，统一证券标识符，对股市中4000余家公司建立“别名库”（简称、旧称、品牌名、英文名），保证能匹配到标准全称。
1.2、介绍下MinHash-LSH和SimHash
MinHash-LSH算法：MinHash是一种局部敏感哈希算法，能够快速估计两个文档的Jaccard相似度。我们将每篇新闻分解为k-gram特征集合（k=3），然后通过多个哈希函数生成MinHash签名。具体实现中，我们使用128个哈希函数，每个函数生成一个MinHash值，最终形成128维的MinHash向量。
LSH（Locality Sensitive Hashing）用于加速相似度计算。我们将128维MinHash向量分成16个band，每个band包含8个值。只有当两个文档在至少一个band中的MinHash值完全相同时，才认为它们是候选相似对。这样可以将O(n²)的复杂度降低到O(n)，大大提高了大规模数据的处理效率。
SimHash算法：SimHash是一种基于特征权重的哈希算法，特别适合处理文本相似度。我们将新闻文本转换为TF-IDF特征向量，然后通过随机投影生成SimHash指纹。SimHash的优势在于能够捕捉语义相似性，即使文本表达方式不同，只要核心内容相似，也能被识别出来。
1.3、数据是怎么打标的
考虑到10万条数据的规模，我们采用了"人工标注 + 大模型标注 + 一致性验证"的半自动标注流程：
第一阶段：人工标注种子数据
我们首先从10万条数据中随机抽样1000条（1%），由专业的金融分析师进行人工标注。这1000条数据作为"种子数据"，用于制定标注规则，以及从中采样数据作为few-shot交给大模型。标注内容包括情感/风险得分以及打分理由。
第二阶段：大模型批量标注
基于1000条人工标注数据，设计了专门的Prompt模板，让多个大模型（GPT、Doubao、Deepseek）对剩余的9.9万条数据进行标注。在Prompt里写明了清晰的评分标准和示例，并要求模型给出标注理由。
第三阶段：一致性验证和人工复审
对于多个大模型标注不一致的样本（情感和风险各自大约5k条），由人工进行重新标注。然后又随机采样了1000条大模型标注一致的样本，由人工进行复核，计算Kappa系数为0.85，说明大模型和人类的评价标准高度一致。

1.4、标注规则怎么制定的
风险分析：目标是衡量新闻揭示的未来不确定性和潜在损失程度。
1（极低风险）：新闻几乎没有不确定性，未来发展高度确定，例如国家强力支持、确定性政策落地、公司基本面稳定。
2（低风险）：存在轻微不确定性，但整体利好或中性。例如政策利好虽已公布但仍需执行落地，企业业绩虽稳健但可能受外部环境波动影响。
3（中等风险）：存在一定不确定性，但影响有限；可能导致短期波动。例如个别高管事件、行业政策调整但不致命。
4（高风险）：事件有重大不确定性，可能导致较大损失；例如监管调查、业绩大幅下滑预期，市场炒作。
5（极高风险）：重大负面事件，未来高度不确定且潜在损失巨大，例如财务造假、退市风险、严重法律/合规问题。
情感分析：目标：衡量市场的即时情绪反应，体现短期影响。
1（极负面）：新闻引发市场极度恐慌，投资者情绪一边倒悲观，股价通常会出现暴跌或跌停，抛售情绪蔓延，市场氛围高度负面。例如公司被证监会立案调查、财务造假曝光、退市风险公告、严重法律或合规问题。
2（负面）：新闻带来明显的不利影响，但恐慌程度有限，市场情绪整体偏悲观，股价可能下跌但幅度有限，投资者以谨慎观望和部分抛售为主。例如高管个人事故、阶段性业绩下滑、一般性的负面舆情、监管问询但未定性。
3（中性）：新闻内容整体中性或利好与利空互相抵消，市场情绪保持平稳，没有明显的乐观或悲观倾向，股价波动幅度较小。例如业绩公告符合预期、例行管理层变动、行业日常动态、宏观经济数据与市场预期一致。
4（正面）：新闻传递积极信号或利好信息，市场短期情绪趋向乐观，投资者信心增强，股价一般会出现上涨，市场氛围偏向积极。例如公司中标大额订单、发布创新产品、政策倾向支持行业发展。
5（极正面）：新闻引发市场极度亢奋，投资者情绪高度乐观，资金大举流入，股价可能连续涨停或大幅上涨，市场氛围普遍高涨甚至带有非理性追捧特征。例如公司宣布进入热门赛道（AI、元宇宙等）引发概念炒作、突发政策大利好、行业出现爆炸性增长预期。

观察新闻里是否提及 市场反应（暴涨、暴跌、追捧、抛售）。
如果新闻本身中性，但市场会解读为利好/利空，要根据市场反应倾向打分。
与风险不同，情感更偏向“短期情绪波动”，而非长期不确定性。
1.5、怎么理解风险分析和情感分析？
风险分析：衡量不确定性和潜在损失
关注点: 事件的不确定性程度、可能带来的负面影响
时间维度: 未来可能发生的不利情况
情感分析：衡量市场情绪和短期影响
关注点: 市场对新闻的即时反应和情绪倾向
时间维度: 当前的市场情绪状态
举几个例子：
新闻: "某AI概念股连续5个涨停，公司宣布进军人工智能领域，股价暴涨200%"
风险: 5 (极高风险) ， 概念炒作，缺乏实际业绩支撑，存在大幅回调风险
情感: 5 (极正面) ， 市场极度乐观，追涨情绪浓厚
新闻: "国家发布新能源汽车补贴政策，补贴金额增加50%，相关产业链受益"
风险: 2 (低风险) ， 政策确定性高，政府支持力度大
情感: 4 (正面) ， 政策利好，市场情绪积极
新闻: "某公司涉嫌财务造假，证监会立案调查，股价跌停，可能面临退市风险"
风险: 5 (极高风险) ， 财务造假是最严重的风险，可能退市
情感: 1 (极负面) ， 市场极度恐慌，抛售情绪浓厚
新闻: "公司某高管出车祸意外死亡，但公司经营正常，业绩稳定"
风险: 3(中等风险) ， 个人问题不影响公司基本面
情感: 2 (轻微负面) ， 负面新闻影响市场情绪



1.6、Kappa系数怎么算
Po（Observed Agreement）：观察到的实际一致率
Pe（Expected Agreement）：期望的一致率（随机情况下）

Kappa值越大说明一致性越强，一般Kappa>0.8就认为标注标准清晰可靠。
举个例子：
构建混淆矩阵
2. 计算Po（实际一致率）：Po = (15 + 20 + 25 + 18 + 16) / 122 = 94 / 122 = 0.770
3. 计算Pe（期望一致率）
Pe = Σ(行总计 × 列总计) / 总样本数²
Pe = (19×18 + 27×27 + 33×34 + 24×24 + 19×19) / 122²
Pe = (342 + 729 + 1122 + 576 + 361) / 14884 = 3130 / 14884 = 0.210
4. 计算Kappa系数：Kappa = (0.770 - 0.210) / (1 - 0.210) = 0.560 / 0.790 = 0.709

2、新闻分析Agent是怎么训练的
新闻分析agent根据股票的最近新闻信息进行分析，我们首先基于用户查询，搜索该股票相关的5条网络新闻（我们建立了一个专业媒体库，包括财新、21世纪经济报道、证券时报等几十家可靠信息源头，避免引入非权威媒体的消息）然后交给大模型进行分析。但发现大模型只会复述新闻，分析浮于表面，请金融同学分析了大量新闻后，发现能从新闻中提取出两个对股票发展比较重要的因素：情感和风险，情感衡量的是这则新闻中公司发展向好还是不好（比如利润下降、股价下跌预示公司发展不好），风险衡量的是公司面临的风险有多大（比如关税政策、同行竞争压力、债务逾期等会加大公司风险）。

我们采用了LoRA技术来微调Qwen3-8B模型，具体细节为：
数据格式：新闻文本+评分理由+评分
LoRA技术细节：设置了rank=16，alpha=32的LoRA参数，只训练了约0.1%的模型参数，大大降低了计算成本和显存需求。
学习率策略：使用余弦退火学习率调度，初始学习率2e-5
优化器设置：AdamW优化器，weight decay设为0.01，beta1=0.9，beta2=0.999
训练参数：batch size为16，gradient accumulation steps为4。
混合精度训练：开启fp16混合精度
硬件配置：两张A100 80G GPU，训练时间约12小时，训练1个epoch
早停策略：将原始数据集按照8:1:1划分为训练集：验证集：测试集，监控验证集性能，防止过拟合
我们在测试集上的结果为：情感模型准确率89.3%，风险模型准确率87.1%。后续我们挖掘了500条难负样本，混合了2000条普通样本进行训练，最终情感模型准确率91.2%，风险模型准确率88.4%。

2.1、难负样本都有哪些类别？
我们为风险模型和情感模型分别人工抽样了500条模型回答错误的样例，主要类别有：
情感模型：
讽刺和反语：使用积极词汇描述负面情况，或者用消极词汇描述正面情况，形成语义上的矛盾。模型需要理解词汇的表面含义和实际表达的情感倾向之间的差异。例如："这家公司业绩'亮眼'，亏损额创历史新高"。表面积极词汇"亮眼"，实际表达负面情感。
复杂情感混合：这类样本同时包含积极和消极的情感元素，形成复杂的情感结构。金融新闻中经常出现"机遇与挑战并存"的情况，一个事件可能带来多个方面的影响，既有正面也有负面。模型需要能够分解复杂情感，识别各个情感成分的权重和重要性。例如"新产品技术领先，但价格过高影响市场接受度"，这种情况需要模型对整个新闻进行更深入的分析。
正面情感预测判断准确率略低：正向情感的新闻预测F1至只有81.4%, 我们分析因为训练数据中情感为正向的新闻显著少于情感为负面和中性的新闻，这些新闻绝大多数都是中性的财报、公司占率调整新闻和负面的公司爆雷、处罚新闻，而正向新闻较少，于是后续又爬去并过滤得到了约2万条的情感正向新闻，重新进行模型训练。
风险模型：
专业知识欠缺：比如财务指标变化，指标本身的风险程度需要结合行业特点、公司发展阶段、历史数据等综合判断。财务指标往往有行业标准，不同行业、不同发展阶段的公司对同一指标的容忍度不同。模型需要具备财务分析能力，理解指标背后的业务含义。例如："xx公司资产负债率65%" ，这需要结合行业特点、公司发展阶段判断风险程度。
复杂风险混合：包含市场环境的多条变化，需要模型进行综合的分析。例如："新能源汽车补贴政策退坡，但公司已提前布局高端市场，技术领先优势明显，同时海外市场需求强劲"。
另外考虑过用FinR1模型替代Qwen3-8B，但由于Qwen3-8B准确率已经达到预期了，暂时还没有继续做这个方向。

2.2、难负样本训练是怎么做的
在难负样本训练时，我们采用4：1的比例混合正常样本和难负样本，即每5个样本中包含1个难负样本和4个正常样本，这样既能让模型学习困难样本，又不会忘记基本的预测能力。使用余弦退火学习率调度，初始学习率2e-5。对难负样本使用Focal Loss，α=0.25，γ=2.0，这样可以让模型更关注难样本的学习。Focal Loss能够自动降低简单样本的权重，增加困难样本的权重，有效解决样本不平衡问题。难负样本再训练我们设置了1个epoch，batch size为16，使用梯度累积steps=4。最终情感模型准确率91.2%，风险模型准确率88.4%。

3、情感和风险模型部署做了哪些优化
模型部署架构：在生产环境中，我们部署了两个独立的推理服务：情感分析服务和风险分析服务，每个服务都运行在独立的Docker容器中，通过RESTful API接口提供服务。
模型量化优化：为了提升推理速度，我们对两个模型都进行fp8量化，将模型大小减少50%。量化后的模型在单张A100 GPU上推理速度提升2.5倍，单次推理时间从200ms降低到80ms。同时我们保持了量化后的模型精度，情感模型准确率仅下降0.3%，风险模型准确率仅下降0.5%。
vLLM推理优化：我们引入了vLLM推理框架，专门针对大语言模型的推理进行优化。vLLM通过PagedAttention技术实现了高效的显存管理，支持动态批处理和连续批处理，能够自动处理不同长度的输入序列。通过vLLM优化，我们的推理吞吐量再提升1.5倍，从40 QPS提升到60 QPS，同时显存使用效率提升了40%。
批处理优化：实现了智能批处理机制，将多个用户的请求进行动态批处理，将相似长度的文本进行批处理，充分利用GPU的并行计算能力。我们还实现了请求队列管理，当请求量超过处理能力时，会自动进行排队和优先级调度。
通过以上优化，我们的两个模型在生产环境中表现稳定，平均响应时间控制在50ms以内，峰值吞吐量达到60QPS，服务可用性达到99.9%。模型推理的稳定性和效率为我们的金融分析系统提供了强有力的技术支撑。

4.1、工具调用失败2%是什么原因，怎么优化？
一方面是数据源API或者服务器网络有问题，另一方面是模型能力问题，他输出的function call命令不正确，导致无法调用工具。
解决方法有：
增加更多多数据源：接入Wind、同花顺等备用数据源，MCP工具调用失败时自动切换至备用源。

升级重试策略：采用指数退避重试，区分网络超时、接口异常等错误类型，避免盲目重试。
工具健康监控：实时监控MCP工具可用性，频繁发生故障时自动下线并触发告警，避免无效调用。

5、详细介绍一下每个Agent负责的工作
我们设计了四个专业智能体：基本面分析、技术分析、估值分析、新闻分析。这样设计是因为金融分析需要多维度视角，每个智能体专注于自己的专业领域，通过并行执行提高效率。我们使用LangGraph的StateGraph管理工作流，确保所有智能体完成分析后，总结智能体再进行结果整合。
具体来说，每个智能体都有明确的职责分工：
基本面分析Agent主要负责分析公司的财务状况和经营能力，包括公司的盈利能力、成长空间、运营效率、负债情况等指标。这个Agent关注的是公司的长期发展，比如赚钱能力强不强，发展前景如何，主要供长期投资参考。
技术分析Agent主要负责分析股票的市场表现和技术指标，包括股价走势、成交量、技术指标等。这个Agent关注短期指标，如最近的涨跌情况，现在买入是否合适，什么时候卖出，主要供短期投资参考。
估值分析Agent主要负责分析股票的价值评估，它会调用相关估值工具获取市盈率、市净率等指标，与业内平均水平进行对比，分析估值变化趋势和股息数据，提供投资建议。这个Agent关注价格是否合理，进行横向对比和估值分析。比如市盈率表示股价是盈利的多少倍，这个值越大你能赚到的就越少。举个例子，如果你有100块，A股票100块一股，每股盈利10块；B股票10块一股，每股盈利2元，只考虑市盈率的情况下你应该买B股票。
新闻分析Agent主要负责分析公司相关的新闻，它会爬取相关新闻，调用我们训练的情感分析和风险预测模型，分析新闻对公司的风险评估和情感影响。这个Agent能够识别新闻中的关键信息，评估对公司发展的影响程度。
总结Agent负责汇总前四个Agent的分析结果并生成markdown格式的报告。
5.1、举个例子说明这几个Agent的关系
用购买手机来类比理解前四个Agent的关系：基本面分析评价手机性能如何；技术分析评价手机销量和价格波动如何；估值分析评价这个手机是否值这个价，跟其他品牌手机对比划不划算；新闻分析评价手机相关的新闻，比如新政策对手机的影响、新品发布、供应链变化等，比如国补政策能更便宜的买到手机，苹果出17后16就会降价。

6、如何保证系统的安全性？特别是金融数据的敏感性？
Prompt注入防护
我们实现了安全防护机制，分为两个层面：
通用安全防护：使用正则表达式对用户输入进行预处理，检测包含恶意指令、系统命令、越权操作等危险内容的输入。系统会识别常见的Prompt注入模式，如"以系统管理员身份执行"等，一旦检测到立即阻止。
金融领域安全防护：建立了专门的金融安全词汇库，包含1000+个敏感词汇和不当表达，如"内幕交易"、"市场操纵"、"洗钱"、"虚假信息传播"等。系统会使用命名实体识别，实时扫描用户输入，检测是否涉及金融违规行为或不当投资建议。
此外还使用了结构化输出解析器，我将用户查询和输出封装在预定义的安全模板中，防止用户查询绕过安全限制，输出不符合模板就按错误信息重试。
智能体行为约束
我们基于LangChain的StateGraph实现了智能体的执行路径控制，定义了智能体的状态转换规则，每个智能体只能按照预定义的路径执行，无法跳转到未授权的状态。每个Agent前后挂策略检查（参数 schema、允许调用的工具、超时），只在通过的情况下才沿着边迁移。此外还支持检查点/回滚（time-travel）便于人工介入与复跑。
输出内容安全控制
当前实现：我们目前使用基于规则的内容审核系统，包含200+条金融安全规则，这些规则涵盖了金融监管要求、合规性检查、敏感词过滤、数值范围检测等多个方面，只有通过所有安全检查的内容才会返回给用户。
未来规划：我们未来会训练专门的幻觉检测模型和数据验证模型。幻觉检测模型专门用于识别AI生成的虚假金融信息。数据验证模型检测输出内容与数据源的一致性，识别虚构的财务数据、不存在的政策法规等虚假信息。

6.1、具体规则有哪些
金融监管要求：检测"内幕信息"、"操纵股价"、"洗钱"等违规表达，如"我提前知道公司要发布重大利好"会被拦截
合规性检查：确保投资建议包含"投资有风险"等必要风险提示，如缺少风险提示的建议会被拒绝
敏感词过滤：过滤"暴涨"、"稳赚"、"包赚"等夸大收益的词汇，如"这只股票包赚不赔"会被拦截

7、具体指标相关
7.1、 投资建议准确率78%是怎么算出来的？
我们基于历史数据进行了回测验证，选取了过去2年的A股市场数据作为测试集，对每只股票的分析建议都进行了跟踪验证，78%的准确率指的是我们的投资建议在后续3-6个月内的表现符合预期。比如我们建议2月1日买入某只股票4月1日卖出，如果这只股票在4.1相比2.1股价上涨了，就算预测正确。

7.2、 数据一致率99%是什么意思？
这个指标衡量的是我们从数据源获取的原始数据的准确性，我们通过多数据源交叉验证来确保数据质量。数据准确率 = (正确的数据条数 / 总数据条数) × 100%。比如模型生成的报告中包含某只股票的市盈率数据，我们会从数据源验证这个数据是否正确，99%意味着每100条数据中，只有大约1条可能存在误差。

7.3、 风险预警准确率85%是怎么评估的？
我们建立了风险预警的评估体系，对100条预警信号进行了后续跟踪验证，准确率 = (正确预警次数 / 总预警次数) × 100%。比如我们的系统发出"某股票存在财务风险"的预警，如果这只股票在后续确实出现了财务问题（如业绩下滑、股价大跌等），就算预警正确。85%的准确率说明我们的风险识别能力还是比较强的。

7.4、 运行故障率小于0.5%怎么计算？
我们建立了完整的监控和日志系统，对每次系统异常都进行了记录和分析。我们的系统平均每天处理1000+次用户查询，一周内出现故障的次数平均不超过50次，故障率小于0.5%的要求。这个指标帮助我们确保系统的稳定性和可靠性。

8.1、RAG打算怎么做

知识融合：在生成阶段，将检索到的相关知识片段与用户查询进行融合，通过Prompt工程指导大模型基于知识库内容生成准确回答

8.2、什么是多级Agent系统
多级Agent系统是一种分层级的智能体架构设计，通过建立不同层级的专业Agent来提升系统的分析精度和效率。在我们的系统中，基本面分析、技术分析、估值分析、新闻分析4个Agent作为一级Agent，每个一级Agent可以进一步拆解为多个专业化的子Agent。比如基本面分析可以拆解为财务健康度分析、盈利能力分析、成长性分析、运营效率分析等多个子Agent。每个子Agent专注于特定领域的分析任务，避免"万金油"问题，提升分析质量，便于针对特定领域进行模型优化和知识库建设。可以训练BERT模型做意图识别选择最合适的Agent组合，支持并行和串行调用，根据问题复杂度灵活调整分析流程，避免不必要的Agent调用，提升系统响应效率。每个子Agent可以独立积累和更新其专业领域的知识，支持Agent间的知识共享和协作学习，理想情况下形成类似辩论室机制，多Agent进行辩论来达成更全面的决策。

8.3、多轮对话怎么实现
上下文管理：客户端保存对话历史，将包括系统、用户和助手角色的每轮对话作为 messages 列表，通过模型调用时完整传入，确保模型能够参考历史上下文。每次新的请求，都把之前的 messages 和当前用户新问题一起提交给模型。使用Redis作为状态存储，设置TTL为24小时，支持断线重连。
上下文压缩和摘要：采用滑动窗口机制管理对话历史，保留最近N轮对话的完整内容（N=5），对更早的对话进行摘要压缩，只保留关键信息，并对历史信息加权，近期对话权重更高。还需要实现指代消解模块，处理"这只股票"、"刚才提到的"等指代词，可以使用BERT做共指消解。


9、金融大模型相关
9.1、为什么使用Deepseek R1蒸馏数据
选择DeepSeek-R1进行数据蒸馏有以下几个技术考虑：首先，DeepSeek-R1在推理任务上表现优异，特别是在数学和逻辑推理方面，这与金融场景的需求高度匹配。我们在实验中发现，DeepSeek-R1生成的推理过程在金融领域具有更好的可解释性，推理链条更加清晰。第二，相比闭源模型，使用DeepSeek-R1进行蒸馏在成本上更可控，且可以保证数据的隐私性，这对于金融数据尤为重要。最后，我们在实验中发现DeepSeek-R1生成的推理过程在金融领域具有更好的可解释性，推理链条更加清晰，当时对比了包括Qwen3-235B-A22B、Doubao-1.5-thinking-vision-pro等模型，采用了100条数据等推理链，人工测评Deepseek-R1效果更好。

9.2、GRPO的奖励怎么设计的
我们设计双重奖励机制是因为金融场景的特殊需求。
格式奖励：主要检查三个方面：第一，模型是否严格按照要求的格式输出，包含完整的think和answer标签；第二，推理过程是否结构清晰，步骤分明；第三，最终答案是否放在正确的位置。我们用规则来检查这些格式要求，确保模型输出的规范性。
准确率奖励（也就是前边提到的语义正确性）：我们使用Qwen2.5-Max作为判别器来评估答案的正确性。这里特别重要的是处理数值匹配问题，因为金融数据中存在多种数值表达形式。比如，标准答案可能是"13.1%"，而模型回答可能是"13.12%"；或者标准答案是"46184055450.1"，而模型回答是"$46.18 billion"。传统的字符串匹配会认为这些答案错误，但实际上它们在语义上是等价的。


9.3、训练数据怎么构造的
数据质量控制我们采用了多层过滤机制。首先，我们选择了业内认可度高的开源数据集如FinQA、ConvFinQA等（数据格式都是QA对）。对于专有数据集，我们构建了严格的多阶段处理流程：从PDF到markdown的批量处理，用正则化技术提取Q-A对，然后进行人工审查和验证。在数据蒸馏阶段，我们用Qwen2.5-Max作为裁判评估DeepSeek-R1生成的响应正确性。最后通过七维度评估筛选高质量推理轨迹。整个过程确保了数据的准确性和推理质量。
我们建立了严格的三阶段数据质量控制体系，确保数据的高质量和多样性。
数据涵盖9个高质量开源数据集如FinQA、ConvFinQA等和私有数据集。整个数据集覆盖34个核心类别：金融专业知识（20%）、金融推理知识（30%）和金融非推理知识（50%）。
三阶段质量控制流程：
数据蒸馏阶段：使用DeepSeek-R1生成思维链数据，严格按照官方规范设置温度0.6，采用标准提示"请使用\boxed{}包裹最终答案"确保格式一致性，并在每个输出开头强制添加"\n"保持推理模式一致性。
答案检查阶段：使用Qwen2.5-Max作为裁判模型，评估DeepSeek-R1生成的响应准确性。这一步确保了基础答案的正确性。
推理选择阶段：基于七个维度对推理轨迹进行质量评分：内部一致性、术语重叠率、推理步骤数、逻辑连贯性、内容多样性、任务领域相关性和与任务指令的一致性。
私有数据集主要是PDF格式的金融考试题，使用Mineru批量处理转换为markdown格式，用正则化技术提取结构化Q-A对，所有提取的数据都经过人工审查和验证过程。
通过这个完整的质量控制体系，我们确保了60,091条训练样本的高质量，同时通过多源异构设计保证了数据的多样性和代表性。

9.4、7个训练推理数据评估方法是怎么设计的
传统的BLEU、ROUGE主要关注文本相似度和词汇重叠，但对于推理质量评估是不够的。我们设计的七个维度是专门针对推理任务特点设计的（都是写prompt让大模型评估），每个维度都有具体的计算方法和评估标准：
第一个维度是内部一致性，我们检查推理链条中前后步骤是否逻辑一致，比如如果前面说"由于利率上升"，后面就不能说"因此债券价格上涨"，这违反了金融常识。我们通过依存句法分析和逻辑关系抽取来计算一致性得分。
第二个维度是术语重叠率，我们构建了金融领域术语库，包含股票、债券、衍生品等专业词汇，计算模型输出中正确金融术语的使用比例。这确保模型掌握了金融专业知识。
第三个维度是推理步骤数，我们统计从问题到答案的推理步骤数量，步骤太少可能缺乏深度，步骤太多可能冗余。我们通过分析think标签内的推理过程来计数，理想的推理步骤在3-7步之间。
第四个维度是逻辑连贯性，我们检查每一步推理是否都有明确的依据和前因后果关系。比如"因为A，所以B"这样的逻辑链条是否完整，我们使用规则引擎和LLM判别器来评估。
第五个维度是内容多样性，我们计算推理过程中使用的不同概念和观点的数量，避免重复和单一化。通过TF-IDF和主题建模来量化多样性。
第六个维度是任务领域相关性，我们评估推理过程是否始终围绕金融问题展开，不偏离主题。通过计算与金融关键词的相关性来评估。
第七个维度是指令一致性，我们检查模型输出是否严格按照要求的格式输出，包含完整的think和answer标签。
我们还验证了人工标注者和模型评估的相关性，发现Qwen2.5-72B-Instruct与人工判断的相关系数达到0.87，这证明了我们评估框架的有效性。相比传统指标，我们的框架能更准确地反映推理质量，为后续的强化学习训练提供了可靠的奖励信号。


9.5、SFT和RL的训练数据格式
SFT阶段数据格式： 每条训练样本包含三个部分(x, c, y*)
x: 问题
c: 推理过程，格式为 <think>...</think>
y*: 标准答案，格式为 <answer>...</answer>
在SFT训练时，输入是问题x，输出是推理过程c和答案y*的完整序列。这样设计让模型学习"先推理、再回答"的结构化思维模式，生成合理的推理步骤和准确的答案，因此需要完整的思维链作为监督信号，以培养模型的逻辑推理能力。
RL阶段数据格式： 每条训练样本包含两个部分
x: 问题（question）
y*: 模型输出答案，不包含推理过程，只保留 <answer>...</answer> 格式的结果
RL训练是为了提升答案准确性和格式规范性，主要通过奖励信号引导模型生成更好的答案。不需要显式的推理过程监督。

11、为什么要用多agent
用多Agent主要出于以下几个原因：
多个Agent解耦了单一Agent的功能，用一个Agent的话就要把所有功能都堆进去，prompt 和工具调用会非常复杂，一但出现错误时很难排查，多Agent调试会更方便一些。
多Agent拓展性更强，未来有新的需求，可以直接增加，而单个Agent只能改prompt和逻辑，会导致越来越臃肿。
金融股票咨询信息链条很长，这个项目里就涉及了基本面、技术面、估值、新闻四个模块，单个Agent难以同时兼顾这么多模块，不如拆分成多个Agent让各自只负责自己的部分。
担心多agent导致的累积误差的话可以加一个校验Agent或者工具，每个Agent分析完都要进行结果校验，减少错误传递现象。
12、用户询问的问题不在agent主链路内怎么解决
意图识别 + 路由分发：在入口处加一个意图分类层（可以用LLM做，也可以用轻量分类模型），识别出用户意图后路由到对应的agent或skill。主链路覆盖不了的意图，走通用问答agent，或者直接告诉用户不要问无关问题。
知识库兜底：接一个RAG模块，把产品FAQ、业务文档、历史对话等都灌进向量库，主链路没命中的问题先走检索，有结果就直接回答
分层降级策略：主链路agent → 领域知识库RAG → 通用大模型兜底，三层逐级降级。这样覆盖面广，同时保证核心场景的回答质量                              
用户反馈闭环：把回答不了的问题记录下来，定期分析，高频问题补充到主链路或知识库里，这是持续迭代的思路
面试官想听的不是某一个工具怎么调，而是你对整个系统架构的思考。
13、项目怎么结合高并发、分布式    
异步处理：多个agent的调用可以异步并发执行，比如股票数据获取、新闻抓取、情感分析这几个agent可以并行跑，用asyncio或者celery做任务调度

介绍一下MCP协议，与function calling有什么区别？
MCP（Model Context Protocol）定义了一套标准化的工具发现、调用和管理机制。MCP协议的核心思想是让AI模型能够动态发现和使用各种工具，实现能力的扩展。MCP协议的主要特点包括：首先，它支持动态工具发现，AI模型可以在运行时发现新的可用工具，无需重新训练或部署。其次，它提供了标准化的工具接口定义，包括工具名称、描述、参数格式、返回值等，确保工具调用的规范性。第三，它支持多种传输方式，包括stdio、HTTP、WebSocket等，适应不同的部署环境。最后，它有良好的错误处理机制，能够优雅地处理工具调用失败、参数错误等异常情况。
与传统的function calling相比，MCP协议有几个明显优势：首先，function calling通常需要将工具函数直接集成到模型代码中，工具更新需要重新部署整个系统，而MCP协议支持动态工具发现，可以在运行时添加新工具，大大提高了系统的灵活性。其次，function calling缺乏标准化的工具管理机制，不同工具的参数格式、返回值格式可能不一致，而MCP协议提供了统一的工具接口规范，确保工具调用的规范性。第三，function calling通常只能在单个应用中使用，而MCP协议支持跨应用的工具共享，一个MCP服务器可以被多个客户端使用，提高了工具的复用性。
在这个项目中，使用FastMCP框架实现了MCP服务器，将各种金融数据工具（如股票数据、财务数据、新闻数据等）封装成MCP工具。智能体通过MCP客户端发现这些工具，然后根据分析需要选择合适的工具进行调用。这种设计使得我们的系统具有很强的扩展性，新增数据源或分析工具只需要实现MCP接口，无需修改核心代码。

为什么可以用矩阵A和B来近似表达
因为矩阵具有稀疏性，矩阵的秩表示的时矩阵的表达能力。秩表示的是矩阵的信息量。如果矩阵中的某一维，总可以通过其余维度线性推导而来，那么对模型来说，这一维的信息是冗余的，是重复表达的。因此，全参数微调中的增量权重可能也存在冗余的信息，所以我们并不需要用完整的尺寸来表示它。

ReAct
ReAct的任务解决轨迹是Thought-Action-Observation，可以简化为模型按照Reasoning-Acting框架。Reasoning包括了对当前环境和状态的观察，并生成推理轨迹。这使模型能够诱导、跟踪和更新操作计划，甚至处理异常情况。ReAct的每一个推理过程都会被详细记录在案，这也改善大模型解决问题时的可解释性和可信度；Acting在于指导大模型采取下一步的行动，比如与外部源（如知识库或环境）进行交互并且收集信息，或者给出最终答案。
GRPO相关
GRPO的核心思想是通过组内相对奖励来优化策略模型，而不是依赖传统的批评模型（critic model）。具体来说，GRPO会在每个状态下采样一组动作，然后根据这些动作的相对表现来调整策略，而不是依赖一个单独的价值网络来估计每个动作的价值。
这种方法的优势在于：
减少计算负担：通过避免维护一个与策略模型大小相当的价值网络，GRPO显著降低了训练过程中的内存占用和计算代价。
提高训练稳定性：GRPO通过组内比较来估计优势函数，减少了策略更新的方差，从而确保了更稳定的学习过程。

K2 估计器：，有偏低方差
K3 估计器：，无偏低方差
GRPO采用了K3 估计器，因为这种估计没有偏差，且方差较低，能更好的近似KL-散度。

为什么GRPO训练开始时，Loss函数为0？
在OpenR1和trl中实现的single step update的GRPO中，损失函数等于 倍平均KL散度；在一开始，policy model和ref model的输出概率一致的，因此KL=0，损失为0。

去掉评估模型，GRPO可能面临的问题
奖励估计不准确：Critic Model的核心作用是评估状态或动作的长期价值。在某些任务中，奖励可能只有在完成特定的长期目标后才能获得，这种场景中失去Critic Model会导致奖励估计不准确，从而导致训练不稳定。
以下是DAPO论文中总结的GRPO面临的问题：
熵崩溃：策略的熵（不确定性）逐渐趋近于零，导致智能体行为过于确定化，失去探索能力。
奖励噪音：奖励信号存在随机波动或误差，导致模型接收到的奖励信息不准确、不稳定，从而影响策略学习的效果。
训练不稳定：在强化学习模型的训练过程中，性能指标（如奖励、损失等）出现大幅波动、震荡或不收敛的现象，导致模型无法稳定地学习到有效的策略。

DPO相比于GRPO的缺点
DPO依赖大量人工标注的偏好对比数据(preferred vs rejected)，需要专业人员进行一致性标注，并且标注质量直接影响模型效果（标注质量不佳很容易导致训练不稳定），存在主观性和不一致性问题。而GRPO可以直接利用奖励信号，无需配对数据。
DPO 是off-policy 训练方法，使用固定的偏好数据集，缺乏在线学习能力，无法根据模型当前状态动态调整训练策略，难以处理分布外的新场景和任务。而GRPO可以在线采样和优化，能够探索新的响应空间。
DPO主要优化偏好排序，目标相对单一，GRPO可以结合多种奖励信号和约束条件。
DPO训练不稳定，因为DPO计算两个响应(preferred vs rejected)的概率差，当概率比值变化剧烈时会产生极大梯度值，导致训练震荡。同时，随着训练进行，当前模型与固定参考模型的差距越来越大，当偏移过度时DPO的理论假设失效，训练完全失控。此外DPO对样本质量和超参数极其敏感。
对比PPO、GRPO、DPO：
GRPO：一组prompt经过LLM生成N个结果，每个结果打分，超过平均的被接受，反之被拒绝
PPO：一组prompt经过LLM生成结果，对结果打分，和上一个的自己比较，有优势被接受，反之被拒绝
DPO：提前构造好了拒绝和接受的数据，模型参数往接受的方向调整
deepspeed
Stage 1：分割优化器状态  ZeRO 的第一个阶段将优化器状态（如 Adam 优化器中的一阶和二阶动量）分布到多个 GPU 上，减少每个 GPU 上的冗余内存占用。
Stage 2：分割梯度  在此阶段，不仅优化器状态被分割，模型的梯度也会在多个设备之间分割和存储，进一步减少显存开销。
Stage 3：分割参数  在最后的阶段，模型的所有参数也会被分布到各个 GPU 上，这样每个 GPU 只保存一部分参数，从而显著节省显存。这一阶段使得单个 GPU 能够训练数千亿参数的模型。

VLLM
vllm是先进的大语言模型推理框架，核心技术是PagedAttention。PagedAttention通过将KV（Key-Value）缓存划分为固定大小的块（类似于虚拟内存中的页），实现了对内存的高效管理。这种设计允许系统根据实际需求动态分配和管理显存，从而提高了推理速度和资源利用率。
优化策略
连续批处理：利用连续批次操作完成多个序列的推理，提高了GPU的利用率。
调度与抢占：采用先来先服务的调度策略，并在需要时抢占资源，以处理更多的请求。
分布式管理：优化了通信机制，提高了系统的扩展性和性能。
PagedAttention的优点
页按需分配：PagedAttention 将每个请求的 KV Cache 拆分为若干固定大小的页，并仅在生成新 tokens 时按需分配物理页，无需提前为最大序列长度预留内存，从而大幅降低 KV Cache 内存占用。
跨请求 KV Cache 共享：相同前缀的多个请求可共用 KV pages，大幅降低内存占用，适用于beam search、A/B test等场景。
消除zero-padding：传统方法往往需将所有序列填充到同一最大长度，导致短序列浪费大量内存和计算。PagedAttention 只在实际需要的 blocks 上分配内存，短序列不会因对齐而被额外填充，从而zero-padding问题被根本杜绝。
提升推理吞吐：由于减少了内存浪费和碎片，GPU 可以在同等显存下加载更多并发请求，vLLM 的实测表明 PagedAttention 能带来 2–4× 的整体吞吐提升，且在中长序列下优势更明显。

Continuous Batching 
在大模型推理时，不再等一批请求都到齐才统一处理，而是把不同请求的 token 按时间轴拼接成一个“大批次”连续送入显卡，每个请求的状态（KV Cache）单独维护。
具体来说：
普通 batching 需要“齐头并进”，一批请求里最短的结束后，长请求还要继续跑，GPU 利用率会下降。
Continuous batching 会把已经结束的请求踢出去，把新来的请求动态加入，把它们的输入 token 和历史 KV Cache 合并在一起，这样 GPU 始终保持高并发。
关键点是显存里要独立保存每个请求的 KV Cache，并用调度器管理不同请求的进度，才能保证模型对每个用户的上下文是独立正确的。
Langgraph相关
介绍下Langgraph框架
LangGraph 是 LangChain 团队推出的有状态图（Stateful Graph）框架，核心定位是用于构建复杂、有状态、多角色的智能体（Agent），通过图形化流程编排（节点 + 边）实现多步骤、多分支、带记忆的任务流程，弥补了 LangChain 在复杂流程管控和状态持久化上的不足。
Langgraph的核心理念是基于状态的有向图执行：
以状态为核心载体，所有节点共享并修改全局状态；
以有向图为流程骨架，通过 节点逻辑，边定义流程流转关系；
以可控执行为目标，支持条件分支、循环终止、外部干预，实现复杂任务的精细化管控。
Langgraph的核心组件
State：全局数据容器，存储任务全生命周期的所有数据（如用户输入、工具输出、中间结果等），支持只读 / 可写权限控制，是节点间数据交互的唯一桥梁；
Node：封装具体任务逻辑的执行单元，可对应大模型调用、工具执行、数据处理等操作，每个节点接收 State 作为输入，执行后返回更新后的 State；
Edge：定义节点间的流转关系，分为 普通边（固定流转，如 A 节点执行后必到 B 节点）和条件边（根据 State 中的数据动态判断流转方向，如按工具执行结果分支）；
Graph：核心编排容器，分为StateGraph（无循环的有向图）和RecursiveGraph（支持循环的递归图），负责注册节点、定义边、启动执行流程；
Checkpointer（检查点）：负责状态的持久化与回溯，支持将每一步的 State 存储到本地文件、数据库（如 SQLite/PostgreSQL），实现任务中断恢复和流程审计。
Langgraph对比AutoGen
AutoGen： 是会话驱动的，多 Agent 之间通过对话交互，聚焦多 Agent 间对话式分工协同。
LangGraph： 是状态/流驱动的。它不假设 Agent 必须通过对话交互，而是通过共享 State。它提供了极高的确定性和控制力，适合构建生产级别的、需要精确业务逻辑控制的 Agent 应用。
Langgraph 执行效率优化方向
状态优化：精简 State 字段，移除冗余数据，避免大体积状态的频繁传输和存储；
节点优化：对耗时节点（如大模型调用、向量检索）进行异步化改造，避免同步阻塞；缓存高频节点的执行结果（如固定查询的工具返回值）；
流程优化：减少不必要的节点和循环，通过并行执行提升并发效率；合理设置分支条件，避免无效流程流转；
部署优化：采用异步运行时（如 AsyncIO），部署为分布式服务分担压力；对外部依赖（如数据库、工具 API）进行性能优化，减少等待时间。
LangGraph 如何实现“人类在环（Human-in-the-loop）”？
LangGraph 实现 Human-in-the-loop 主要依赖于 Checkpointer 和 Interrupt的结合。具体实现分为三步：
持久化配置 (Persistence)：在编译图（Compile）时配置一个 checkpointer（如 MemorySaver 或 PostgresSaver）。这是基础，它确保了图的状态可以被保存到数据库中，从而允许流程暂停和恢复。
设置中断 (Interruption)：
方式一（架构级）： 在 compile 时设置 interrupt_before=["tool_node"]。框架会在执行指定节点前自动挂起。
方式二（逻辑级）： 在节点内部使用 interrupt() 函数（LangGraph 新特性），根据业务逻辑（如 need_review=True）动态触发中断。
状态干预与恢复 (Intervention & Resume)：
当流程暂停时，人类可以通过 graph.get_state() 查看当前上下文。
如果有误，使用 graph.update_state() 修改状态（例如修正 LLM 的参数）。
最后，使用相同的 thread_id 再次调用 invoke（传入 Command(resume=...) 或 None），图会从断点处继续执行。
Langgraph怎么实现记忆机制
短期记忆（上下文记忆）：主要负责当前会话的上下文维持。 这通过 State Schema 结合 Checkpointer 来完成。具体来说，在 State 中定义 messages 字段（配合 add_messages reducer）来存储对话历史，同时利用 Checkpointer 基于 thread_id 对状态进行持久化快照。这确保了在同一个会话线程内，系统能够维护上下文连贯性，并支持断点续传。
长期记忆（持久化记忆）：主要负责跨会话的知识复用。 通过 LangGraph 的 Store API 来实现的。Store API 允许通过定义独立的 Namespace（如 user_id），将从对话中提取的用户画像或关键信息存储在全局的键值库中。

Langgraph里多agent之间的记忆机制
LangGraph框架下多Agent记忆架构以有状态图执行为核心，基于LangChain生态实现记忆的分层管理与流转，核心设计为私有记忆+全局共享记忆的双层结构，所有记忆统一挂载在框架的全局State中，与Agent节点执行、边的条件跳转深度绑定，适配多Agent协作的状态一致性需求。
私有记忆为单Agent独有，存储其专属任务记录、工具调用历史等个性化信息，仅所属Agent可读写；全局共享记忆为所有Agent公共访问，包含对话历史、任务目标、中间执行结果、共享知识库向量数据等，支持指定Agent的修改权限控制。
记忆流转遵循图执行逻辑：初始化全局State完成记忆冷启动，Agent节点执行时从State读取所需私有/共享记忆，执行后将结果写回对应记忆区域，节点间跳转时自动继承最新State状态，任务结束可通过检查点实现记忆持久化，同时支持记忆摘要、修剪、向量检索增强等扩展能力，兼顾记忆的有效性与轻量化。
